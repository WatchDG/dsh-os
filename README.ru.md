# dsh-os

[![CI](https://github.com/WatchDG/dsh-os/actions/workflows/ci.yml/badge.svg)](https://github.com/WatchDG/dsh-os/actions/workflows/ci.yml)
[![License: Apache-2.0](https://img.shields.io/badge/license-Apache--2.0-blue.svg)](LICENSE)

[English](README.md) | **Русский**

Правила ОС и оболочки для [DeepSeek Harness](https://www.deepseek.com/en/harness/):
бандл-плагин, который закрывает типовую ошибку агентов — они пишут
POSIX-синтаксис (`&&`, `$NAME`, `export`, `/usr/bin/...`) на Windows, где
команды выполняет PowerShell, а `&&` в Windows PowerShell 5.1 — синтаксическая
ошибка.

Плагин определяет ОС и оболочку, даёт переключатели в **Настройки → Терминал**
и подставляет агентам короткий блок правил, соответствующий выбранной паре.

## Требования

| Требование | Детали |
|---|---|
| [DeepSeek Harness](https://www.deepseek.com/en/harness/) | 0.2.x. Плагин использует сервис `systemPrompt` хоста и скоупы `settings` / `webServer`. |

Внешних бинарников нет, сетевого доступа нет, шага сборки нет.

## Установка в DeepSeek Harness

Плагин — это бандл профиля DSH, поэтому он действует на все сессии этого
профиля.

1. Откройте страницу **Plugins** в боковой панели DSH (Plugin Manager).
2. Нажмите **Add plugin** / **Install bundle**, выберите этот каталог
   (тот, где лежит `package.json`), и подтвердите.
3. Убедитесь, что **OS & Shell Rules** / **Правила ОС и оболочки** включён
   в списке плагинов.

Тот же шаг доступен агенту через инструмент `plugin_manager` с
`action: install_bundle` и абсолютным путём к каталогу. DSH записывает в
`package.json` профиля зависимость `link:` на каталог; поскольку каталог
связан, после обновления файлов плагина перезапустите DSH, чтобы хост
загрузил новый JavaScript.

Удаление — через Plugin Manager (или `plugin_manager` с
`action: remove_bundle`).

## Что делает плагин

### 1. Правила

Одна секция системного промпта `os-shell:rules` вставляется сразу после
штатных инструкций shell-инструментов (`tool:pwsh` / `tool:bash`). Она
объясняет модели:

- чем чейнить команды (`;` в PowerShell, `&&` в bash/cmd);
- как читать и задавать переменные (`$env:NAME`, `$NAME`, `%NAME%`);
- как писать пути и какие команды использовать вместо POSIX-аналогов;
- что каждый вызов — новый процесс: нужен `workdir`, а не `cd`;
- как вызывать другую оболочку, если выбранная не совпадает с инструментом
  (`cmd /c "…"`, `bash -lc '…'`, `pwsh -NoProfile -Command '…'`);
- как проверять коды возврата (`$LASTEXITCODE`, `%ERRORLEVEL%`);
- ловушки ОС: блокировки файлов и зарезервированные имена на Windows,
  блокировки OneDrive/Defender, переводы строк CRLF/LF (`.gitattributes`),
  потерянные биты исполнения (`chmod +x`), симлинки,
  чувствительность к регистру, правильный пакетный менеджер, `py`
  против `python3`, `start` / `open` / `xdg-open`, `NUL` против `/dev/null`
  и кодировочные грабли 5.1;
- какой разновидности bash соответствуют пути на Windows (Git Bash `/c/...`
  против WSL `/mnt/c/...`);
- что подключение `remote` описывает сторону SSH, а не этот хост;
- указатель на глобальную таблицу анти-паттернов POSIX → native.

### 2. Переключатели, определение и превью

Страница **Настройки → Терминал**:

- карточка «Определено на этом хосте: Windows · PowerShell» — то, что
  автоопределение реально видит, плюс инструмент (`pwsh`), из которого
  взята оболочка, определённая разновидность bash, `$SHELL`/`ComSpec` хоста,
  shell-инструменты агента (`pwsh`/`bash`) и шаблон обёртки, если выбранная
  оболочка отличается от инструмента;
- бейдж удалённой сессии, когда правила описывают машину по SSH, а не хост;
- если выбор пользователя отличается от определения, отдельная строка
  показывает, что сейчас используют правила;
- пять списков: операционная система, оболочка, разновидность bash (только
  для bash на Windows), подключение (`local` или удалённое по SSH) и версия
  PowerShell (`auto` безопасна для 5.1, `7` разблокирует пометки про `&&`/`||`);
- read-only превью точного текста `os-shell:rules`, который увидит агент
  (отдаёт тот же маршрут `GET /os-shell/status`, с кнопкой копирования и
  рабочим примером команды для пары).

Оба поля — *volatile* Config: запись применяется на месте, без перезагрузки
плагина, и действует со следующего шага модели. Уже запущенный шаг сохраняет
промпт, с которым начался.

### 3. Файлы тем (topics)

Ядро правил содержит только директивы разрешённого контекста — без сравнений,
чужих оболочек и пакетных менеджеров. Заканчивается указателем, который
называет контекст (`Windows + PowerShell`, а при bash — с разновидностью:
`Windows + bash (WSL)`) и детальные файлы: `topics/os-<os>.md` (файлы,
установки, консоль, пути), `topics/shell-<shell>.md` (коды возврата, скрипты,
процессы), `topics/commands-<os>.md` (нативные аналоги команд), а для
удалённых сессий — ещё и `topics/ssh.md`. Вторая ссылка всегда ведёт на
глобальную таблицу `topics/anti-patterns.md` (привычка POSIX → что реально
принимает каждая оболочка). Агент читает нужный файл инструментом `read`,
когда тема «кусается», — указатель содержит абсолютные пути от места
установки бандла, поэтому работает везде, а чужие контексты агент не видит.

## Автоопределение

- **ОС** — `process.platform` процесса хоста (там же выполняются команды
  агента): `win32 → Windows`, `darwin → macOS`, иначе `Linux`.
- **Оболочка** — сначала смотрится реестр инструментов: если у агента есть
  `pwsh`, это PowerShell; если `bash` — bash. Это точнее переменных окружения,
  потому что именно этот инструмент исполняет команды. Если инструментов нет —
  `$SHELL` на POSIX (по умолчанию `zsh` на macOS, `bash` на Linux) и
  PowerShell на Windows.

- **Разновидность bash (только Windows)** — WSL-маркеры в окружении
  (`WSL_DISTRO_NAME` / `WSL_INTEROP`) означают WSL (`/mnt/c/...`), всё
  остальное — Git Bash (`/c/...`). Процессы для проверки не запускаются.
  Вне Windows разновидность всегда `native`.

Значение `auto` в полях `os`, `shell`, `bashFlavor` и `powershellEdition`
включает это определение. Явный выбор имеет приоритет. Поле `location` по
умолчанию `local`; выберите `remote`, когда команды выполняются на другой
машине по SSH, — тогда правила описывают удалённую сторону, а не хост.

Определение для страницы берётся из последней сборки промпта — там известен
scope агента и его инструменты. До первой сборки страница показывает
определение по окружению хоста (`source: 'host'`); после неё — по инструментам
агента (`source: 'agent'`).

Если выбранная оболочка не совпадает с той, что исполняет инструмент, правила
не врут: они показывают обёртку для явного вызова (`cmd /c "<command>"` и т. п.).

Данные для карточки отдаёт самодостаточный маршрут `GET /os-shell/status`
(тот же браузерный trust-fence, что у остальных API: без аутентификации — 401).

## Настройка

| Поле | Значения | По умолчанию |
|---|---|---|
| `os` | `auto`, `windows`, `macos`, `linux` | `auto` |
| `shell` | `auto`, `powershell`, `cmd`, `bash`, `zsh`, `fish`, `sh` | `auto` |
| `bashFlavor` | `auto`, `git-bash`, `wsl`, `native` | `auto` |
| `location` | `local`, `remote` | `local` |
| `powershellEdition` | `auto`, `5.1`, `7` | `auto` |

Все поля доступны и в файле патча профиля (строка `id: os-shell`):

```yaml
- id: os-shell
  config:
    os: windows
    shell: bash
    bashFlavor: wsl
    location: local
    powershellEdition: auto
```

`powershell` покрывает и Windows PowerShell 5.1, и PowerShell 7. При
`powershellEdition: auto` (или `5.1`) правила безопасны для 5.1: `&&`/`||`
запрещены, цепочка — через `;`. Выбирайте `7`, только если точно знаете, что
цель — PowerShell 7+.

## Проверка

1. На странице **Plugins** (и в read-only списке **Settings → Plugins**) есть
   **OS & Shell Rules** / **Правила ОС и оболочки**, плагин включён.
2. Клиентская страница зарегистрирована в живом слоте `settings.section`
   (`id: os-shell`, `order: 17`, `active: true`) — значит, хост отдаёт
   namespace `os-shell`, и форма настроек подключена. Страница показывает
   карточку определения, пять списков и read-only превью точного текста
   правил с кнопкой копирования и примером команды.
3. В новой сессии субагент дословно возвращает первый абзац
   `## Terminal environment`, включая «through the `pwsh` tool» —
   срабатывает определение оболочки по инструменту агента (scope), а не по
   глобальному реестру.
4. Отключение и повторное включение строки `include:os-shell` через Plugin
   Manager убирает и возвращает секцию в промпте без перезапуска приложения.
5. Маршрут `GET /os-shell/status` зарегистрирован и защищён: `POST` на него
   без браузерной аутентификации получает 401 от общего trust-fence, а тот же
   `POST` на несуществующий путь уходит в SPA-fallback и получает 405 — то есть
   маршрут существует и отвечает именно он. Полезная нагрузка дополнительно
   несёт `preview`, `example`, `wrapper`, `tools` и определённые/целевые
   flavor, location и edition.
6. `npm test` — юнит-проверки схемы Config, определения, разновидностей,
   обёрток, текста правил, владения страницей настроек и маршрута статуса,
   плюс проверки манифеста.
7. `npm run preview -- --os windows --shell bash --bash-flavor wsl` печатает
   разрешённую секцию в stdout без запущенного Harness.

Визуальная проверка карточки и реальное сохранение кликом выполняются
штатно через `configForms` → `settings` — тот же путь, что у страницы Shell.

## Устранение неполадок

| Симптом | Причина / решение |
|---|---|
| Правила называют не ту оболочку | Карточка показывает источник: `host` до первого шага агента, `agent` после. Проверьте, какие инструменты есть у агента (`pwsh` побеждает `bash`). Для `windows + bash` смотрите строку разновидности: Git Bash и WSL по-разному монтируют диски. |
| Правила описывают не ту машину | Возможно, выбран `remote`: тогда правила намеренно описывают сторону SSH. Для этого хоста верните `local`. |
| Выбор не применяется | Записи volatile действуют со следующего шага модели; запущенный шаг хранит свой промпт. Если правился JS хоста — выключите и включите строку бандла. |
| Нет страницы «Терминал» | Хост отдаёт namespace, только пока строка бандла включена; проверьте страницу Plugins и перезапустите DSH после обновления файлов. |

## Разработка

Одна зависимость (`@deepseek-ai/schemastery` для схемы настроек), шага
сборки нет.

```bash
npm ci                   # установить библиотеку схемы настроек
npm test                 # юнит-тесты и проверка манифеста
npm run test:unit        # те же наборы, явным списком
npm run preview -- --os windows --shell bash --bash-flavor wsl
npm run pack:check       # проверить состав npm-пакета
```

Структура:

```
index.js              точка входа хоста: экспортирует apply / name / inject / Config
client.js             страница Настройки → Терминал: карточка определения, списки, превью правил (веб-клиент)
preview.mjs           CLI-превью разрешённых правил без запущенного Harness
lib/config.js         схема Config, значения по умолчанию, нормализация, живой снапшот
lib/env.js            чистое определение ОС/оболочки/разновидности и разрешение окружения
lib/rules.js          текст правил и позиция секции
lib/plugin.js         подключение к контексту (секция промпта + роут /os-shell/status)
topics/               контекстные пакеты, на которые ссылается ядро
                      (os-<os>.md, shell-<shell>.md, commands-<os>.md, ssh.md, anti-patterns.md)
test/                 наборы node:test (env, rules, plugin, status, topics, manifest)
```

Если добавляете runtime-модуль, добавьте его в `files` в `package.json`;
иначе тест манифеста упадёт. См. [CONTRIBUTING.md](CONTRIBUTING.md).

## Безопасность и приватность

- Плагин не запускает процессы, не ходит в сеть, не отправляет телеметрию и
  не хранит историю команд. Страница настроек обращается только к
  собственному аутентифицированному роуту хоста `/os-shell/status`.
- Плагин не переписывает команды и не блокирует их: он даёт правила. Уже
  запущенный шаг сохраняет промпт, с которым начался.
